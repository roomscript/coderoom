# POC: Claude Code via bidirectional stream-json

## Goal

Validate that one long-running Claude Code process can be driven over stdin/stdout with the stream-json protocol the Agent SDK uses: multiple turns, host-answered tool approvals, interrupt without killing the process, and stop/resume. This replaces the May conclusion that only one process per turn with `--resume` works (`poc-claude-msg-continuation.md`).

---

## Setup

- Claude Code 2.1.300, model `haiku` (`claude-haiku-5-5`). Haiku was enough for every experiment.
- Invocation (from `playground/claude-stream-json/session.go`):

```
claude --print --verbose \
  --input-format stream-json --output-format stream-json \
  --replay-user-messages --include-partial-messages \
  --permission-prompts host --permission-prompt-tool stdio \
  --model haiku
```

- Personal config (plugins, MCP servers, skills, `CLAUDE.md`, memory) loads normally, the same way coderoom starts Codex. `--safe-mode` was tried in E9 and kept only as documented context (`-safe-mode` flag in the playground).

- Environment: inherited, minus the variables a parent Claude Code session exports (`CLAUDECODE`, `CLAUDE_CODE_*`, `CLAUDE_PID`, `CLAUDE_EFFORT`). The Agent SDK also drops `CLAUDECODE` for the same reason.
- Each experiment runs in a fresh temp directory.
- Fixtures: `playground/claude-stream-json/fixtures/*.jsonl`. They are local only (git-ignored) and regenerated by the Make targets; the protocol shapes that matter are quoted in this report. Line 1 is a `meta` header (version, args, dir). Then one entry per line with `t_ms` and `dir`: `in` (stdin), `out` (stdout), `stderr`, or `note` (harness events and observations). Raw lines are under `json` (or `text` if not JSON).
- Fixtures are redacted when written: account `email` and `organization`, `$HOME` replaced with `~`, `$USER` replaced with `user`.

## What changed since May

| May finding | Now (2.1.300) |
|---|---|
| `--input-format stream-json` exits without reading stdin | Process stays alive, reads stdin, and keeps context across turns |
| Personal config cannot be suppressed without breaking auth | `--safe-mode` works with the OAuth login and removes most personal config (E9). Not used by default |
| Fallback: one process per turn with `--resume` | Not needed. `--resume` still works and is useful after a stop or crash (E8) |

## Protocol as observed

### Input (stdin)

One JSON object per line.

```json
{"type":"control_request","request_id":"req_1","request":{"subtype":"initialize","hooks":null}}
{"type":"user","message":{"role":"user","content":"..."},"parent_tool_use_id":null,"session_id":"default"}
{"type":"control_request","request_id":"req_2","request":{"subtype":"interrupt"}}
{"type":"control_response","response":{"subtype":"success","request_id":"<id from CLI>","response":{"behavior":"allow","updatedInput":{...}}}}
{"type":"control_response","response":{"subtype":"success","request_id":"<id from CLI>","response":{"behavior":"deny","message":"..."}}}
```

The SDK source shows more control subtypes (`set_permission_mode`, `set_model`, `mcp_status`, `get_context_usage`, `rewind_files`). They were not tested.

### Output (stdout)

| Message | When | Notes |
|---|---|---|
| `control_response` | reply to our `control_request` | `response.request_id` matches. The initialize reply has `commands`, `agents`, `models`, `account`, `pid`, `claude_code_version`, `current_permission_mode`, `session_state` |
| `system/init` | start of **every** turn | session id, model, cwd, tools, MCP servers, plugins, skills, `permissionMode`, `capabilities` |
| `system/status` | `status: "requesting"` before each API request | |
| `user` with `isReplay: true` | our message echoed, about 1.5 s after sending, just before the model starts streaming | has its own `uuid` and `timestamp` |
| `stream_event` | partial messages | raw Anthropic streaming events: `message_start`, `content_block_start/delta/stop`, `message_delta`, `message_stop` |
| `assistant` | each complete content block | `message.content[]` of `text`, `thinking`, `tool_use` |
| `user` with `tool_result` | after each tool runs | `tool_use_result` carries structured data (see E5) |
| `control_request/can_use_tool` | tool needs approval | see E3 |
| `system/permission_denied` | a tool call was denied | |
| `system/thinking_tokens` | during reasoning | |
| `system/task_updated`, `system/task_notification`, `system/background_tasks_changed` | background task progress | see E10 |
| `command_lifecycle` | a scheduled (cron) prompt starts and completes | see E10 |
| `rate_limit_event` | once per turn | |
| `result` | **end of turn** | `subtype` `success` or `error_during_execution`, `is_error`, `terminal_reason`, `result` (final text), `session_id`, usage and cost, `permission_denials`, `structured_output` |

Turn boundary: one `result` per turn. Every turn starts with a new `system/init`. A turn we started is preceded by our message echoed back (`isReplay: true`). A turn Claude started on its own (background task finished, cron fired) has no replay (E10).

## Experiments

### E1: idle start

- No output before the first input. Still alive after 10 s idle with no TTY: the May hang does not happen.
- `initialize` gets a reply in under 3 s. `system/init` is **not** emitted on initialize. It comes with the first user message, and again on every later turn.
- Closing stdin when idle: clean exit (code 0) in about 1 s.

### E2: two turns

Context kept ("7" recalled). End of turn is the `result` message. The session id is the same across turns.

### E3: approvals

- **Required flag:** `--permission-prompt-tool stdio`. With only `--permission-prompts host` (the default), approval prompts never reach the host. They are denied automatically ("Claude requested permissions to write to … but you haven't granted it yet") and reported as `system/permission_denied`. To reproduce, remove `--permission-prompt-tool stdio` from `baseArgs` in `session.go` and run E3. The SDK always adds `--permission-prompt-tool stdio` when a `can_use_tool` callback is set.
- Request shape:

```json
{"type":"control_request","request_id":"…","request":{"subtype":"can_use_tool","tool_name":"Write","display_name":"Write","input":{"file_path":"…","content":"yes\n"},"description":"allowed.txt","permission_suggestions":[{"type":"setMode","mode":"acceptEdits","destination":"session"}],"tool_use_id":"toolu_…"}}
```

  Bash requests can also carry `blocked_path`, plus suggestions such as `addRules` and `addDirectories`.
- Allow writes the file. Deny (`behavior: "deny"` with a message) leaves no file, and the model sees the message. The denial appears in `result.permission_denials`, and the session stays usable.
- Read-only Bash commands (`ls -la`, `pwd`, `cat`) ran **without** a prompt in the default permission mode. `cd sub`, `touch`, Write and Edit prompted.

### E4: interrupt

- `control_request` with `subtype: "interrupt"` works. The reply arrives within a few ms. The turn ends 25 to 40 ms later with `result` `subtype: "error_during_execution"`, `is_error: true`, `terminal_reason: "aborted_streaming"`.
- The process survives, and the next turn works normally. No signals needed.
- A few `text_delta` events already in flight still arrive after the interrupt is sent.

### E5: partial messages

One turn with reasoning, Bash, Write, Edit and Bash again. Fixtures: `e5-partials.jsonl` and `e5-partials-thinking-summarized.jsonl`.

- **Text:** `content_block_delta/text_delta`, then a complete `assistant` text block.
- **Reasoning:** by default, `thinking_delta` events arrive with **empty text** (only `estimated_tokens`), and the `thinking` block has only a `signature`. With the hidden flag `--thinking-display summarized` (an SDK option; values `summarized` and `omitted`), the reasoning text streams (a few hundred characters per run).
- **Tool call:** `content_block_start/tool_use`, `input_json_delta` chunks, then an `assistant` `tool_use` block with `id`, `name` and `input`.
- **Tool result:** a `user` message with a `tool_result` block (`tool_use_id`, `content`, `is_error`) plus a structured `tool_use_result`:
  - Bash: `{stdout, stderr, interrupted, isImage, noOutputExpected}`. Output keeps ANSI colour codes (`ls` colours). This run had no failing command. **Correction (later probe):** a failing command has `is_error: true` and `tool_use_result` is a string, `"Error: Exit code N\n<stdout>\n<stderr>"`, so the exit code is in the text. See "Bash results and exit codes" in `docs/design/pkg-agent-claude.md`.
  - Write: `{type: "create", filePath, content, structuredPatch: [], originalFile: null}`.
  - Edit: `{filePath, oldString, newString, originalFile, structuredPatch: [{oldStart, oldLines, newStart, newLines, lines: ["-hello", "+hello world"]}]}`.

Mapping to coderoom content types (details left for phase 2):

| Claude | coderoom |
|---|---|
| `text_delta` / `assistant` text | `Output` |
| `thinking_delta` (needs `--thinking-display summarized`) | `Reasoning` |
| `tool_use` Bash + its `tool_result` | `Command` (exit code parsed from failure text) |
| `tool_use` Write/Edit + `tool_use_result.structuredPatch` | `FileChangeSet` |
| `can_use_tool` | `ApprovalRequest` |
| `result` | turn end / flush |

### E6: cwd

- Started from Go (a non-shell parent) with `cmd.Dir` set to the project dir and `PWD` inherited from a different directory: Bash `pwd` returns the project dir. The same happens with `PWD` set explicitly. The May issue does not reproduce.
- `cd sub` in one Bash call carries over to the next Bash call in a later turn: the shell cwd is session state, as in an interactive session.

### E7: `--json-schema`

- The schema becomes a `StructuredOutput` tool that is available on **every** turn of the process. When the model calls it, `result.structured_output` holds the object and `result.result` holds its JSON string. The model still streams a free-text answer first.
- It is **not enforced**. In the first run (with `--safe-mode`), all three turns called it, even "Say hello in one word". In the run without `--safe-mode`, the model skipped it on the greeting and asked which claim to judge: `subtype: "success"`, `structured_output: null`.
- For a `/decide` turn this means a dedicated process (or a `--resume`d fork), plus a check for `structured_output: null`.

### E8: stop and resume

- Close stdin: clean exit, code 0, about 1.1 s.
- SIGTERM while idle: exits in under 1 s with code 143.
- Both sessions resumed in a new process with `--resume <session_id>`: same session id, context restored ("pineapple", "mango").

### E9: `--safe-mode`

A project with a `CLAUDE.md` rule ("end every reply with BANANA") and a project allow rule `Bash(touch:*)`, run with and without `--safe-mode`:

| | normal | `--safe-mode` |
|---|---|---|
| Auth (OAuth login) | ok | ok |
| Project `CLAUDE.md` | honoured | **ignored** |
| MCP servers | your claude.ai connectors (pending) | none |
| Plugin skills (`anthropic-skills:*`) | 13 | none |
| Auto memory | `memory_paths` set | none |
| Agents | 5 (incl. `statusline-setup`) | 4 built-in |
| Tools / slash commands | 28 / 66 | 27 / 53 |
| Installed plugin `gopls-lsp` | loaded | **still loaded** |
| Built-in skills | present | present |
| Project allow rule `Bash(touch:*)` | prompted anyway | prompted anyway |

- `--safe-mode` works with your login. It is the cleanest isolation available, but it also drops the project's `CLAUDE.md` (the counterpart of the `AGENTS.md` Codex reads).
- **Decision:** not used. coderoom does not restrict Codex's personal config either. Isolation belongs to the sandbox work (#59). This table is kept as context for that work.
- The allow rule test is inconclusive. The prompt carried `blocked_path` and suggested adding the cwd as a directory, so a path check (the temp dir is under `/tmp`) won over the rule in both modes.

### E10: tools that ask, act outside a turn, or reach outside the room

Each variant ran in its own process. `SendMessage`, `PushNotification` and `RemoteTrigger` were not triggered, because they have real effects outside the playground.

**`AskUserQuestion`: an approval with answers.** It arrives as a normal `can_use_tool` request with `tool_name: "AskUserQuestion"`:

```json
{"questions":[{"question":"…","header":"Color","multiSelect":false,"options":[{"label":"Red","description":"Choose red"},{"label":"Blue","description":"Choose blue"}]}]}
```

- To answer, send `behavior: "allow"` with `updatedInput: {questions: <as received>, answers: {"<question text>": "<label>"}}`. Multi-select takes an array of labels. An optional `response` field carries free text instead of answers. The model replied "Blue".
- To dismiss, send `behavior: "deny"` with a message. The model sees the message and asks again in plain text.
- So it fits the approval mechanism as a new approval kind whose decision carries answers.

**Plan mode (`--permission-mode plan`): another approval.**
- The model first wrote its plan to `~/.claude/plans/<name>.md` **without a prompt**. That file is outside the project directory.
- It then called `ExitPlanMode`, which arrived as `can_use_tool` with `input.plan` (markdown). Allowing it let the model leave plan mode and continue. The Write that followed prompted normally.

**Background Bash: Claude starts a turn on its own.** `run_in_background: true` ended the turn right away with "started". About 6 s later, with nothing sent:

```
system/task_updated (status completed)
system/task_notification (task_id, tool_use_id, status, summary, output_file)
system/background_tasks_changed
system/init                       <- new turn, no replayed user message
stream_event … assistant          "The background command finished with exit code 0."
result/success
```

The output lives in a file (`output_file`). On the next user turn the model read it with `Read`.

**Cron: Claude starts a turn on its own.** `CronCreate` (no permission prompt) with `{"cron":"34 21 15 10 *","prompt":"Reply with just: tick","recurring":false}` fired about 16 s later, at the next minute boundary:

```
command_lifecycle (state started)
system/init                       <- new turn, no replayed user message
stream_event … assistant          "tick"
result/success
command_lifecycle (state completed)
```

**`ListAgents`: the participant sees your other sessions.** It ran without a prompt and returned this session's own name plus the 3 interactive Claude sessions running on the machine (names, tmux panes, busy or idle). The process also gets a `messaging_socket_path` in its init event. `SendMessage` was not tried, so it is unknown whether it would prompt.

**Detection, as observed:**

| Signal | Means | Tools seen |
|---|---|---|
| `can_use_tool` with `tool_name` `AskUserQuestion` / `ExitPlanMode` | the agent asks the human something other than "may I run this" | AskUserQuestion, ExitPlanMode |
| `system/init` with no replayed user message since the last `result` | a turn the agent started on its own; its output reaches `Read` with no `Send` behind it | background Bash, CronCreate |
| `system/task_*`, `system/background_tasks_changed` | background work is running or finished | Bash `run_in_background`, likely Monitor and Task |
| `command_lifecycle` | a scheduled prompt is running | CronCreate |
| `tool_use` name in an `assistant` message | any tool, including those that never prompt | ListAgents, CronCreate, ToolSearch |

Tools that never prompt (`ListAgents`, `CronCreate`, `ToolSearch`, the plan file write) can only be seen through the `tool_use` stream. They can only be blocked up front with `--disallowedTools`.

### E11 to E13: model and effort within a session

Run on 2.1.303 for #71. Design consequences are in `docs/design/pkg-agent-claude-models.md`.

Three control requests, all answered within milliseconds and none starting a turn:

```
{"type":"control_request","request_id":"…","request":{"subtype":"set_model","model":"sonnet"}}
{"type":"control_request","request_id":"…","request":{"subtype":"apply_flag_settings","settings":{"effortLevel":"high"}}}
{"type":"control_request","request_id":"…","request":{"subtype":"get_settings"}}
```

`set_model` and `apply_flag_settings` answer `success` with a null response, or `error` with a message. `get_settings` answers with `effective` (the merged settings files), `sources` (one entry per settings file) and `applied`:

```json
"applied":{"model":"claude-sonnet-5-5","effort":"high","advisor":null,"ultracode":false,"ultracodeRequested":false,"ultracodeAvailable":false}
```

**E11: catalog and settings, no model turn.** The project's `.claude/settings.json` sets `{"model":"sonnet","effortLevel":"low"}` and no `--model` is passed, so the session starts from CLI-managed settings.

- The `initialize` response has `models[]` but no current model. Each entry has `value`, `resolvedModel`, `displayName`, `description`, and, when the model supports effort, `supportsEffort: true` and `supportedEffortLevels`. Values are aliases (`default`, `opus`, `sonnet`, `fable`, `haiku`) and full IDs of older models. The current models' full IDs appear only as `resolvedModel` of an alias.
- `applied` at startup is `{model: claude-sonnet-5-5, effort: low}`: the configured values, with the model resolved to its full ID.
- `effective` did not follow any runtime change in this run. It reflects the settings files, so `applied` is the field to read.

| Step | Reply | `applied` afterwards |
|---|---|---|
| `set_model opus` | success | `claude-opus-5-5`, `low` |
| `set_model sonet` | error `Model 'sonet' not found` | unchanged |
| `set_model` with `model: null` | success | unchanged: a no-op, not a reset |
| effort `high` | success | `claude-opus-5-5`, `high` |
| effort `bogus` | success | unchanged: ignored without an error |
| `set_model sonnet` | success | `claude-sonnet-5-5`, `high`: effort carries over |
| `set_model claude-haiku-4-5-20251001` (no effort support) | success | that model, effort `null` |
| `set_model sonnet` | success | `claude-sonnet-5-5`, `high`: the selection comes back |
| effort `null` | success | `claude-sonnet-5-5`, `medium`: not the configured `low` |
| `set_model default` | success | `claude-opus-5-5`: the account default, not the configured `sonnet` |

Clearing the effort falls back to `medium`, not to the project's `low`. The same happened with the effort passed in `--settings`, which is in the flag layer `apply_flag_settings` writes to. So in both cases a cleared effort does not return to the configured one.

**E12: the conversation survives a model switch.** One `haiku` turn asked the model to remember a word, then `set_model sonnet`, then a second turn asked for the word. The second `system/init` reports `model: claude-sonnet-5-5`, the answer was correct, and the result's `modelUsage` lists both models.

**E13: the effort reaches the API request.** Claude ran with `ANTHROPIC_BASE_URL` pointing to a local stub that records each Messages request's `model` and `output_config` (never headers) and answers with an error, so no quota is used. One turn per step:

| Step | `output_config` sent |
|---|---|
| startup (`--model sonnet`, no effort configured) | `{"effort":"medium"}` |
| effort `low` | `{"effort":"low"}` |
| effort `max` | `{"effort":"max"}` |
| effort `bogus` | `{"effort":"max"}`: the previous value |
| effort `null` | `{"effort":"medium"}` |

So `applied.effort` is what the request carries, and an invalid value is never sent.

## Open questions for phase 2

1. `AskUserQuestion` and `ExitPlanMode` as new approval kinds: how do they extend `ApprovalRequest` and `ApprovalDecision` (a decision that carries answers, or a plan to approve)?
2. Self-started turns (background tasks, cron): coderoom's turn model expects output only after a `Send`. Options: surface them as unsolicited participant output, disable the tools (`--disallowedTools CronCreate,…`), or decide per tool. What does Codex do with background work, if anything?
3. Reaching outside the room: `ListAgents` sees your other sessions without a prompt, and `SendMessage` is untested. Should room participants run with `--disallowedTools ListAgents,SendMessage,PushNotification,RemoteTrigger`, or is this part of the sandbox work (#59)?
4. Bash has no exit code in tool results (only `is_error`; the background notification has it in text). Is that enough for coderoom's `Command`? **Resolved:** failed results carry `Exit code N` in their text; see the correction under E5.
5. Why the project allow rule did not apply (path check under `/tmp`?). Retry with a project dir outside `/tmp`.
6. `--json-schema` is per process and not enforced, so `/decide` needs its own process and a check for a missing `structured_output`.
7. `SendNotice` (a minimal acknowledgment, suppressed from `Read`) has no protocol equivalent. It must be a normal turn whose output is filtered, as with Codex.
8. Turn anchor: the replayed user message has a `uuid` we could map to `StreamID`, but it arrives only about 1.5 s after sending.

## How to run

```
cd playground
make pg-claude-stream-json        # all experiments (live, uses your Claude login)
make pg-claude-stream-json-e3     # one experiment (e1..e13)
cd claude-stream-json && go run . -redact-fixtures   # re-apply redaction to existing fixtures
```

`make pg-…` from the repo root currently does nothing ("Nothing to be done"). The root Makefile declares the playground targets `.PHONY`, and GNU make skips pattern rules for phony targets. This affects the existing `pg-codex-*` targets too.
